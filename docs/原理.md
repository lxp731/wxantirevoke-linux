# 原理

## 微信怎么处理撤回

微信 PC 4.x（Windows / macOS / Linux 同源 C++ 代码）收到撤回时的流程：

1. 收到系统消息（`<sysmsg type="revokemsg">` 或等价的协议结构）；
2. 由 `parseRevokeXML` 系列函数解析，把被撤回消息的 **`newmsgid`** 存进消息对象
   （Linux 上是 `+0x1c8`）；
3. 用这个 `newmsgid` 找到**原消息**，把它的内容替换成"xxx 撤回了一条消息"。

所以只要让第 3 步匹配不上原消息，原消息就会留下来。

## 本项目的补丁（唯一一处，5 字节）

```
VA 0x60df783   (文件偏移 0x60de783，/opt/wechat/wechat 4.1.13.26)

  原: E8 B8 9E 2D 01     call 0x73b9640      ; 从 <newmsgid> 节点取出 uint64
  新: 31 C0 90 90 90     xor eax,eax; nop×3  ; rax = 0
```

紧跟其后的是 `0x60df788: mov [rbx+0x1c8], rax` —— 于是存进消息对象的 `newmsgid` 恒为 0。
后续应用链拿到的 `newmsgid` 全是 0，匹配不到任何原消息，**原消息保留**；
而撤回提示是独立插入的，所以**提示照常出现**。

这么做有上游依据：

| 平台 | 上游做法 | 位置 |
|---|---|---|
| macOS | `wechat-antirecall` 的 `revoke-tip` 模式：`str x0,[x19,#newmsgid]` → `str xzr` | 其文档结论即 **"把 newmsgid 写零 —— 微信因此保留原消息但仍显示撤回提示"** |
| Windows | RevokeMsgPatcher 对 4.1.7+：`mov [rsi+disp],rax` → `sub [rsi+disp],rax` | 同一思路的另一种实现 |

本项目在 Linux 上做的是同一件事。

## 实际调用链（探针实测）

```
收到撤回
  └─ parseRevokeXML(0x60df1e0)                  解析 <newmsgid> → 消息对象 +0x1c8
       └─ 0x6adc230 APPLY
            ├─ 0x60ecaa0   构造撤回提示 sysmsg（type="revokemsg"）
            ├─ 0x6514320   按 newmsgid 查原消息（全二进制只有这一个调用点）
            └─ 0x6adcd9c   查不到 → 跳过"覆盖原消息"
```

> 注：`parseRevokeXML` 里 `has("revokemsg")` 那条分支（`0x60df42c`）**实际不会被走到** ——
> 走的是它的 else 分支（`0x60df69e`）。所以想靠改那条分支来防撤回是无效的，
> 详见 [排查记录.md](排查记录.md)。

## 效果与限制

**有效范围**：只影响本机这个客户端。服务器、手机、网页版仍然显示"已撤回"；
重装微信/换机后历史消息也仍是"已撤回"。本质上这是**本地显示层的补丁**。

**已知限制**：

- 撤回提示仍然显示（这是刻意的，与 macOS 版 `revoke-tip` 一致）
- **自己撤回自己发的消息**：同样走这条解析链，所以原文也会保留。若只想要"只防别人"，
  需要再找一个 self/other 判别点（探针里有线索，尚未实现）
- 微信升级会让补丁点失效（见 README「微信升级后」）
- 微信没有做二进制完整性自校验（4.1.13.26 实测），修改内存页可正常启动；
  若未来版本加了校验，需要另行处理

## 静默模式（可选，未实现）

想要连"xxx 撤回了一条消息"都不要，可以试着把 APPLY 函数入口（`0x6adc230`）改成
`xor eax,eax; ret`，整条应用链跳过。风险：该函数可能有其他必要的记账动作，
需要实测验证（用 `wechat-probe` 抓一次调用链即可判断）。
