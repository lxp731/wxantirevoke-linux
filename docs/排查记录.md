# 排查记录：三次尝试，为什么前两次空转

补丁点不是一次找对的。这里把过程完整记下来，避免以后重复走弯路。

## 三次尝试一览

| 版本 | 站点 | 做法 | 结果 |
|---|---|---|---|
| **v1** | `0x60df42c`：`parseRevokeXML` 里 `has("revokemsg")` 的分支 | `0F 84` → `90 E9`（`je` → `jmp`），与 Windows 版 RevokeMsgPatcher 对 4.1.0~4.1.6 的手法相同 | ❌ **空转**。探针证明这条分支**从未被执行**（实际走的是 `je` 的 else 分支 `0x60df69e`），强制跳转 = 原样 |
| **v2** | `0x6514320`（按 newmsgid 查原消息）置为 `return NULL` + `0x6adcd9c`（查找到结果的守卫）强制跳转 | `31 C0 C3 ...` / `0F 84 FB 04 00 00` → `90 E9 FB 04 00 00` | ❌ **空转**。探针显示 guard 处 `rax=1`，而 `jne` 本来就把流程送去同一个地址（`0x6add29d`） |
| **v3** | `0x60df783`：把解析出的 `newmsgid` 取成 0 | `E8 B8 9E 2D 01` → `31 C0 90 90 90` | ✅ **生效**：原消息保留 + 提示仍显示 |

## v1 为什么空转

第一版依据是 macOS 版文档里"`parseRevokeXML` 入口处一条 `cbz` 改成 `b`，跳过删除原消息的逻辑"，
于是照搬到 Linux 上对应的分支：

```
0x60df42a  84 C0                 test al,al        ; al = has("revokemsg")
0x60df42c  0F 84 6C 02 00 00     je   0x60df69e
0x60df432  ...                                     ; 这个"撤回处理"分支从未走到
```

补丁**确实写进了运行中的进程**（`/proc/<pid>/maps` 在 `0x60de000` 处出现一页独立的 COW 私有映射，
只有被 `mprotect` + 写入过的页才会这样），但对方撤回依然生效。

真相在探针数据里（第一次探针会话）：

```
HIT parseRevokeXML(entry)      n=1
HIT   .has_revokemsg判         n=1
HIT   .非revoke分支            n=1     ← 走的是这里
HIT   .newmsgid写入            n=1
HIT revokemsg_xml_builder      n=1
```

**`.revoke分支`（0x60df432）一次都没命中。** 也就是说 Linux 4.1.13 上撤回根本不经过那条
"有 `<revokemsg>` 元素"的分支 —— 它走的是 else 分支，而那个分支同样会解析
`newmsgid` / `chat_id` / `revoke_climsgid`。把 `je` 强制成 `jmp`，跳去的正是它本来就要去的地方，
所以等价于没改。

## v2 为什么空转

v1 失败后，顺着 `newmsgid` 这条线静态分析出应用链：

```
0x6524de0 wrapper → 0x6adc230 APPLY
    ├─ 0x60ecaa0  构造撤回提示 sysmsg
    ├─ 0x6514320  按 newmsgid 查原消息（全二进制仅一个调用点）
    └─ 0x6adcd9c  test r13,r13 ; je skip
```

于是做了两个"更干净"的补丁：让查找函数恒返回 NULL，并把守卫分支强制成"跳过"。
探针这次拿到了完整证据（第二次会话，同时加载补丁 + 探针）：

```
HIT APPLY:wrapper2(entry)         n=1   0x6524de0
HIT APPLY:RevokeApply_fn(entry)   n=1   0x6adc230
HIT APPLY:.build_tip_xml#1        n=1   0x6adcc66
HIT revokemsg_xml_builder         n=1   0x60ecaa0
HIT APPLY:.lookup_by_newmsgid     n=1   0x6adccf9
HIT APPLY:lookup_fn(entry)        n=1   0x6514320   ← 已被改成 return NULL
HIT APPLY:.guard test r13,r13     n=1   0x6adcd99   rax=000000000001
HIT APPLY:.guard_skip_target      n=1   0x6add29d
                    .guard_other_branch   0 次
```

关键在 `rax=1`。那段代码是：

```asm
6adcd91  movzx eax,[rsp+0x920]   ; 一个标志
6adcd99  test  r13,r13           ; r13 = 查找结果
6adcd9c  je    6add29d           ; 查不到 → 6add29d
6adcda2  test  al,al
6adcda4  jne   6add29d           ; 标志≠0 → 也是 6add29d
6adcdaa  <fall-through>
```

标志是 1，所以**这个事件本来就会走 `0x6add29d`**；我把跳转强制到同一个地址，
自然什么也没变。而且查找结果（`r13`）在这条路径上根本没被用到 —— 说明
"覆盖原消息"并不依赖这次查找。

## v3 为什么对

回到 macOS 版文档，它其实把正确做法写得很直白（`revoke-tip` 模式）：

> 把 `str x0,[x19,#0x168]` 改成 `str xzr,…`，**把 `newmsgid` 写零 ——
> 微信因此保留原消息但仍显示撤回提示**。

Windows 版 4.1.7+ 的 `mov [rsi+disp],rax` → `sub` 是同一思路。
所以在 Linux 上找到同一处（解析 `newmsgid` 的地方）动手：

```
0x60df756  lea rsi, "newmsgid"        ; 取成员
0x60df762  call 0x889aae0
0x60df771  call 0x889ab50             ; has value?
0x60df77e  mov rdi, [rsp+0x38]
0x60df783  call 0x73b9640             ; node → uint64  ← 改成 xor eax,eax
0x60df788  mov [rbx+0x1c8], rax       ; 存进消息对象（于是恒为 0）
```

**不动任何分支**，只让流经链条的数据变成"匹配不到任何消息"，因此绕开了前两次踩的坑
（猜分支极性）。

实测结果：对方撤回后原文保留，提示照常显示。✅

## 教训

- 改分支之前，先确认**那条分支在这次事件里到底走哪一边**（探针的寄存器现场直接就有答案）。
  v1 和 v2 的错误本质相同：在证据不足时猜极性。
- v2 的探针日志里 `rax=1` 已经写明了答案，当时没仔细读寄存器，多花了一轮测试。
- 优先采用**上游已经验证过的补丁形态**（macOS `str xzr` / Windows `sub`），
  比自己在反汇编里找分支可靠得多。
