# 探针工具 wxprobe

用途：**在不改变程序语义的前提下，测出微信撤回到底走了哪条代码路径**。
补丁点不是靠猜出来的，就是靠它定位的。

## 原理

把要观察的地址的**第一个字节换成 `0xCC`（`int3`）**，自装 `SIGTRAP` 处理器：

```
命中 → 记录时间戳 + 寄存器现场
     → 还原原始字节（先 mprotect 放开权限）
     → RIP 指回该地址，重新执行那条指令
```

所以程序行为和没装探针时完全一致，只是被执行位置被计数和采样了。

## 用法

```bash
# 完全退出微信后：
wechat-probe          # 补丁 + 探针一起加载（排障推荐）
```

`wechat-probe` 会提示操作步骤。日志在 `~/.local/state/wxantirevoke/probe.log`。

标注测试窗口：

```bash
wxantirevoke-mark     # 在日志里打印所有探针的当前计数快照
```

典型流程：启动 → 等 15 秒（探针在启动 10 秒后才布防）→ `wxantirevoke-mark` →
触发一次真实撤回 → `wxantirevoke-mark`，两个 MARK 之间新增的计数就是这次撤回走的路径。

其他环境变量：`WXANTIREVOKE_LIB=<某个 .so>` 可换成只加载某一个库；
`WXPROBE_LOG=<路径>` 换日志位置；`WXPROBE_DELAY=<秒>` 换布防延迟；
`WXPROBE_EXTRA="0x<VA>:名字,..."` 追加临时探针（自测用）。

## 设计要点（都是踩过坑之后加的）

- **每秒重新布防**：命中一次后该地址会恢复原字节（不然就死循环了），
  启动期的无关命中不会导致错过后面真正的撤回事件
- **每秒抢回 `SIGTRAP`**：微信在进程内装了 crashpad 崩溃处理器，会覆盖我们的处理器；
  抢回时把对方的处理器存下来做链式转发
- **延迟 10 秒布防**：避开启动阶段安装信号处理器的窗口
- **地址越界剔除**：探针 VA 必须落在主程序可执行段内，否则直接跳过
  （微信升级后地址失效也不会把进程搞崩）
- **只对主程序生效**：`/proc/self/exe` basename 必须是 `wechat`，
  `crashpad_handler` / `WeChatAppEx` 等子进程自动跳过

## 开发时踩的坑（三个都会让诊断白做或直接把微信搞崩）

这三个都是用**合成测试**抓出来的 —— 造一个也叫 `wechat` 的测试程序，把探针装到它自己的
函数上反复调用，验证"命中 → 还原 → 语义不变"。合成测试立刻暴露了：

1. **在 `r-x` 页面上直接写回原字节 → `SIGSEGV`**
   处理器里必须 `mprotect(RWX)` → 写 → 恢复 `r-x`。
   这个 bug 如果没测出来，用户第一次撤回就会把微信崩掉。

2. **首次布防没有采样 `saved`（原字节）**
   重新布防的循环里判断 `if (*q != pr->saved) continue;`，而 `saved` 一直是 0 →
   条件永远成立 → **探针从未真正装上**。
   症状很好认：日志里全是 0，**连无关命中都没有**。
   （这就是第一次诊断失败的原因，白等了一轮用户测试。）

3. **处理器里用运行时地址和 VA 比较**
   命中现场 `pc-1` 是运行时地址，探针表里存的是 VA，必须 `g_base + pr->addr` 再比，
   否则永远匹配不上 → `SIGTRAP` 被转给默认处理器 → 进程直接崩。

另外还有一次虚惊：`.text` 段的「文件偏移 = VA − 0x1000」在算 `0x6514320` 时被我手算错
（减成了 `0x10000`），一度以为映射不一致。校验方法：把 objdump 打出的字节序列在文件里搜一遍，
看它落在哪个偏移。
